RuvNet Brain · the architecture

Nine pieces. Take the ones you want.

Most of this is optional, and taking only part of it is a legitimate choice — not a broken install. What has been missing is an honest account of what each piece costs and what its absence costs, in numbers, so you can decide rather than guess. That is this page. Nothing here is trying to talk you into installing more.

“I can't use your stuff because it has hooks and this and that. I just loaded the brain into my RuVector Brain and I don't get the rest of it.”

— a power user, to the owner. He is right, and nobody could tell him what he was missing.

1 · The KB corpus

69 of rUv's repos, chunked, embedded, and stored next to their original text. required ›
What
Repositories walked file by file, split into passages, embedded, and written to RVF vector stores that sit beside the passage text they came from.
Gives
Answers about the rUv ecosystem sourced from rUv's actual code instead of a model's training prior. Every hit is a whole document labelled repo/path, so you can go check it.
Costs
2.7 GB of disk, an 843 MB download. Zero runtime cost when nothing is querying it — no server, no daemon, no port. It is inert files.
Lose
Everything. This is the substrate — the other eight pieces are ways of reaching it or keeping it honest.

Two embedders, from the same passages

Read from the sidecar files, not recalled. *.big.rvf uses bge-base-en-v1.5, 768-dim, CLS pooling, asymmetric — queries carry a prefix, passages do not. Retrieval auto-selects it when present. *.rvf uses all-MiniLM-L6-v2, 384-dim, mean pooling, symmetric: the edge variant, for machines and runtimes that cannot carry the big model.

The corpus is a snapshot, not a mirror — and it says so on every response. Each search_ruvnet answer carries a staleness line computed from the real file mtimes of the stores it queried. That exists because of issue #31 (Jan Lafko): a model quoted a version out of the corpus as though the corpus were live. For anything about "latest" or a dist-tag, check the live registry — the tool now tells you that every single time rather than leaving you to remember it.

2 · The MCP server

Puts exactly one tool inside Claude Code: search_ruvnet. optional90–150 s / call ›
What
Two processes. A thin protocol shell that Claude Code spawns and talks to, supervising a warm child that holds the models and does the retrieval.
Gives
The model can consult all 69 repos mid-answer, without you doing anything. A query fans out to every store, pools the candidates, then re-scores the whole pool in one cross-encoder pass so hits from different repos are comparable.
Costs
One resident Node process holding the embedding models (~0.5 GB). One JSON line per call to the local token ledger. No network. No project files touched. And the latency below, which is real and large.
Lose
The corpus stops being reachable from inside a conversation. You keep every byte and can still query it by hand at ~110 s per question, in a separate terminal, pasting results back yourself. This is exactly the configuration the power user described.

Measured latency — three real round-trips through the MCP protocol

Query (k=6)LatencyResponse
how does agenticow branch memory122.3 s20,020 chars · ~5.0K tok
what is the RVF witness chain91.4 s43,066 chars · ~10.8K tok
ruflo swarm init topology151.4 s7,557 chars · ~1.9K tok

Read that table honestly. A search_ruvnet call is a 1.5–2.5 minute operation on an M3 Max, and it can return 10K tokens. That is the true price of fanning out across 69 stores and re-ranking with a cross-encoder, and it should not be sold as a fast lookup. It earns its cost when the alternative is a confident wrong answer about a tool that already exists — the failure this whole project was built after. It does not earn its cost for a question you could answer by opening one file.

The same retrieval through the CLI took 110 seconds for a single question, because each invocation reloads both models from scratch. The warm child is what amortises that away.

A fixed bug worth knowing, because it is the class of thing this piece could get wrong again. The token meter originally wrote to process.cwd()/.ruvnet-brain/ — and an MCP server inherits its working directory from the Claude Code session, so it scattered hidden folders through users' project trees. Issue #36 (mamd69) reported this against two shell hooks; the MCP server had the identical bug and was not in the report. Fixing only what was reported would have left the symptom alive and made the fix look wrong. All three now write user-level only, keeping the working directory as a data field so per-project analysis survives without writing into a project.

Two of those five are not part of what you install, and saying otherwise would be the exact dishonesty this project exists to kill. A fresh install gets three blocking gates: one inert without opt-in, one that only fires inside this repository. In practice a new user is subject to exactly one — verify-interface. The version-bump-gate lived in global settings until 2026-07-14, taxing every Bash command in 34+ projects with a rule that is true in one. A hook belongs in the narrowest scope where it is true.

What their absence costs, specifically

Grounding
1,986 injections per 10.6 hours become zero. The model consults the brain only when it independently decides to — measured across this project's history, that is the failure mode, not the fallback.
Drift
Four categories of anti-pattern stop watching your writes. Nothing says "you're about to add a server-based vector store; a single RVF file is the database."
Alarm
On 2026-07-12 this brain's dependencies vanished and every search failed for days, invisibly — returning empty results that read as "nothing exists". The four structural checks exist because of that, and they are the only thing that distinguishes a dead brain from a quiet one.
Learning
The queue never fills. It already starved once: the flush originally fired only on a clean session end, so sessions that compacted, crashed, or resumed never reached it. The queue grew to 1,884 undelivered events while the learner sat at 5 trajectories, last trained six days earlier. Draining it took the learner to 412 / 412 in one command.

4 · The stable spine

Lets hook behaviour update without restarting your editor. optional ›
What
Immutable copies of the hook bodies under a versions directory, and a pointer file naming the active one. A single shim is the only thing the hook config names; it resolves that pointer once per invocation.
Gives
Behaviour updates the instant the pointer flips — no Claude Code restart. Claude Code freezes the plugin root at boot, so without this every hook is trapped at the version that was on disk when you opened your editor.
Costs
One small JSON read per hook fire. Disk for retained generations — garbage-collected, with leases so a tree still being served by a running MCP process is never collected out from under it.
Lose
Update correctness, and the ability to know when you have lost it.
Silence has to mean one thing. The shim distinguishes three states and is deliberately noisy about two: a spine that resolves but is missing a body file falls back to the frozen plugin and prints a line naming the fallback; a previously-seeded-but-now-broken spine does the same. Only a genuine first install is quiet. That asymmetry exists so a broken spine can never masquerade as health.

5 · The console

Your machine, mirrored — and reversible one-click fixes. The page you are one click from. optionalread-only by default ›
What
A local page bound to 127.0.0.1 with a random per-launch token, opened with /rvbc.
Gives
Which rUv tools are installed and at what version, which capabilities are dormant, memory health, router utilisation — and fixes you can undo.
Costs
A local HTTP server while it is open. Network reads of the npm registry for the version audit. Writes nothing until you click.
Lose
The ability to see any of this. Every other piece runs headless — the console is the window, not the engine. Its absence costs you discovery, which is precisely the complaint at the top of this page: he owns pieces he has never seen.

Four laws, encoded in code rather than promised

Read-only
Rendering the page and building its state writes nothing.
Re-verify
Apply re-measures the world and refuses any item that is no longer true.
Undo first
The inverse is journalled before the change runs.
Never re-do
Every mutation dispatches to a script that already backs up, verifies against disk, and is idempotent.
A recommendation cannot be constructed without evidence, a cost, and an undo. The factory throws otherwise — and if the change touches the machine it additionally demands a plain-English impact statement of at least 40 characters. That is a type error at construction, not a code review someone can forget. Law 2 exists because on 2026-07-12 two concurrent sessions both wrote a memory checkpoint and one silently destroyed the other's entire state, with no error and only a changed row id as evidence.

6 · The capability registry

Eleven rows answering the flat question: is this one actually on? optional ›
What
Eleven capabilities, each with a live probe — learning hooks, memory distillation, workflow learning, cheap-model routing, cross-project lessons, lessons in force, harness self-improvement, write gates, session capture, connected tools, nightly refresh.
Gives
A row per capability whether the news is good, bad, or unavailable. An audit only speaks when something is wrong, so a healthy capability produces no finding at all — and silence is indistinguishable from "I never looked".
Costs
Eleven read-only probes. It observes; it never installs, enables, or writes.
Lose
The honest form of "you lose proactivity": you lose the flat inventory that distinguishes off from unmeasurable, so a dormant capability and a broken probe look identical. That is exactly how a starving learner sat unnoticed for six days.

Two rules it exists to enforce

“Unknown” outranks “off”, always. Reporting "off" for something you failed to measure is not a rounding error — it is the precise lie this project was built to kill, and it is easy to commit here because every underlying helper has a falsy default. While this file was being written, a live probe of this repo's own memory store returned "unable to open database file". Ninety seconds later the identical query returned 1,201 memories, 99.8% embedded, 596 distilled patterns: the store was fully healthy and the first read had simply lost a race with a concurrent writer. One transient lock, and the console would have told its owner to fix a system that was already working.

No command is offered unless it was run with --help first. Four of the eleven therefore offer no turn-on command at all, each recording the negative check that produced the null so nobody re-litigates it from memory. A confidently-wrong command is worse than none — it sends a person to a shell to be told "unknown subcommand", which costs them trust in every other row on the page.

The most instructive bug in the repository. Every project-scoped detector used to read where the code was installed instead of where the user was standing. From an empty folder it reported "write gates: ON — 6 gates can refuse a write, 203 refusals recorded" — ruvnet-brain's own numbers, presented as yours. From a real project with a healthy 16 MB memory store it reported "memory distillation: ABSENT", with a button offering to fix a problem you did not have. Anyone not standing inside a ruvnet-brain checkout — which is every user — got one of those two.

7 · The lesson store

Your corrections, replayed at the moment they apply. It nudges — it does not force. optionalnudge by default ›
What
Corrections you have given, structured, and surfaced at the decision point where they apply. 15 lessons today — 12 ratified, 3 candidate — across ten decision types: asserting a fact, recommending an architecture, relaying a number, reporting status, writing code, claiming done, shipping, changing the machine, choosing work, finishing.
Gives
You stop re-explaining the same preference. The store currently holds one lesson you have had to give six times.
Costs
One process spawn per matching event, hard-capped at 5 seconds where the timeout utility exists.
Lose
Your corrections stay prose in a file nobody reads at the moment they would have mattered.

One dispatcher, not one hook per lesson

Gates scale with decision types, never with lesson count. Adding a lesson requires no code change anywhere — and that asymmetry is the whole architecture. Without it, every new rule would need its own script, which is the "thousand hooks" outcome the owner explicitly rejected.

It nudges. It does not force.

A lesson may declare that it blocks and still arrive as advisory context unless you have personally opted that lesson into refusing. That is deliberate, and it is the owner's own correction of an earlier design: “Nudging somebody is very fair. Forcing them through a gate is not.”

0
Why that behaviour is shown as a transcript instead of described. On 2026-07-22 the previous version printed “⛔ BLOCKED” and returned exit 0 — three stacked defects, each individually sufficient: the gate exited 1 where the harness requires 2, wrote its reason to the stream exit-2 ignores, and the dispatcher discarded the code entirely. An ADR claimed "five gates refuse the action — proven by exit code". The proof had been obtained by running the CLI by hand, which is the one caller that is not a gate. Never verify a hook by running it the way a hook doesn't.
Fail-open, defined correctly. The old code implemented it as "always allow", which is not the same thing. Failing open means an error must not refuse you — a missing interpreter, an unreadable store, a timeout. It never meant discarding a deliberate refusal. Those are now separated by exit code: one value is a decision and propagates, everything else is a malfunction and allows.

8 · Evergreen + Dream evaluation

Updates installed bytes and evaluates changes without writing the primary checkout. optionalchanges your machine ›
What
An optional installed-cache updater plus a non-merging Dream Machine evaluation cycle.
Gives
Fresh published bytes on installed hosts and evidence-backed improvement proposals without unattended source writes.
Costs
A launchd plist for Evergreen is a real machine mutation, which is why the installer asks for it behind its own flag. Author rebuild CPU and disk are spent only after an explicit clean linked-worktree run.
Lose
Freshness, degrading continuously — but visibly. The staleness line on every search response prints the real age of the stores it queried, so you can always see how bad it has become. You can also refresh by hand at any time.
The primary checkout is not an automation workspace. The former com.ruvnet.brain-nightly source writer was retired after it accumulated generated changes beside active work. Author rebuilds now refuse primary, nested, non-linked, and dirty worktrees and verify afterward that primary HEAD, index, tracked files, and untracked-file set did not change. Dream evaluation cannot merge; Evergreen updates the installed cache only.

A way in that you do not have to remember a file path for.
Costs

Reading this as the power user. Taking only the brain costs you, in numbers: 1,986 grounding injections per 10.6 hours become zero; four categories of drift interception stop watching your writes; the four health checks that catch a silently dead brain stop running — and that failure ran for days on 2026-07-12, returning empty results that read as "nothing exists"; the learning queue never fills; 15 lessons across 10 decision points never surface; and the 11-row audit, the one thing that would have told you any of this was switched off, is not on screen.

What it saves you: ~630 tokens per prompt, ~2,120 per session, three gates that can refuse a shell or subagent call, and any writes under the cache directory. If you are a heavy rUv user the trade favours the full plugin decisively. If you use one rUv tool occasionally and value an uninterrupted shell, brain-only or brain+MCP is genuinely the right shape — and nothing on this page is trying to talk you out of it.

Normally this happens on a per-user basis, which lets learning, intelligence, access and software versions stay updated universally across all your projects. Choose per-project only if this is something you absolutely only use on a per-project basis. Our strong recommendation is per-user — but we always want you to be the arbiter of how things run on your machine.

Nothing below the plugin install is all-or-nothing either. The hook config is a plain file you can trim entry by entry, and the hooks table above tells you exactly what each line does before you delete it.

the limits

What this page does not claim

Not claimed
That every gate blocks. Three do. Two of the five in the refusal ledger are wired in this machine's own settings and are not part of a fresh install. The lesson gate nudges.
Not claimed
That search is fast. It is 1.5–2.5 minutes per call on an M3 Max, measured.
Not claimed
That the corpus is current. It is a snapshot, and every response prints its age in days, per store.
Not claimed
That 69 repos is the ecosystem. 69 built, 123 pending, ~248 in the org.
Not claimed
That any of this was verified on Windows or Linux. Every number came from one macOS machine. The hook config declares itself posix-only.
Not claimed
Anything about YOUR machine. This page is static and reads nothing. For live state — what is installed, what is dormant, what is broken right now — that is the console's job, one click away in the header.

Every figure on this page was produced by running a command on a real machine on 2026-07-22, not recalled. The full write-up, with the command behind each number, is in docs/ARCHITECTURE-MAP.md.
